# CATI multi-asset (crypto + FX): dataset, broker capability, capital routing and auto-activation

Status of this document: **describes what exists in the repository at the commit that adds it.**
Anything not yet built is listed as a blocker or as unsupported, never as done.
Machine-readable companion: [`cati_market_capability_matrix.json`](cati_market_capability_matrix.json)
(generated by `scripts/generate_capability_matrix.py --discover`; it is derived from code and live public

## 1. Executive scope

CATI stays **one** intelligence / risk / execution architecture. Asset classes differ only in context:

```
Market Data -> GlobalMarketState -> asset-class context (FX context) -> Regime -> Setups -> Forecast
 -> Venue/Account economics -> Admission -> Veto -> Whole-universe ranking -> Account portfolio selection
 (cross-asset caps) -> Reservation -> Capital plan (internal routing only if needed) -> TradePlan
 -> Hard risk -> Broker execution -> Reconciliation -> Position forecast -> Exit -> Evidence
```

First-class market families: **CRYPTO** and **FX**. Stocks/ETFs, commodities and indices are discovered,
classified and capability-tracked (TRADFI) with the same machinery; CATI certification for them does not
exist yet.

This work (branch `cati/multi-asset-fx-capital-routing`) closed the gaps left after Phases 2-6:

| Gap found in the audit | Closed by |
|---|---|
| Bybit ETF perpetuals (54 live) classified as CRYPTO | `app/exchange/instruments.py` (unknown venue types -> OTHER; ETF -> STOCK) |
| Bybit FX identity wrong (`EURUSD/USD`) | `fx_legs()` -> `EUR/USD:FX_PERPETUAL` |
| BingX TradFi (614 `NC*` contracts in the official swap API) classified as CRYPTO | `bingx_namespace()` |
| BingX FX/TradFi declared "venue API unavailable" although the official swap contract list exposes them with per-contract `apiStateOpen` | capability now discovery-resolved per instrument (UNVALIDATED -> demo only) |
| No crypto dataset beyond 5 symbols | frozen 136-symbol certification universe + 15m backfill |
| No FX dataset | Dukascopy probe (50 pairs) + hourly broad tier + minute deep tier |
| Certification CLI could not pin a frozen universe | `--universe-manifest` |
| Section 24 `contracts.global_market_state` PARTIAL | GlobalMarketState contract + engine + cycle evidence |
| Currency-exposure graph not enforced in selection | hard `max_net_currency_units` + logical asset-class caps in the selector |
| Finished features parked behind "remember to enable" flags | `app/activation` AUTO_ACTIVE_IF_ELIGIBLE |
| No per-account "what can this account trade" view | `GET /api/v1/brokers/{id}/market-status` |

## 4. CATI multi-asset architecture

Identity is `InstrumentKey` (CATI) / `DiscoveredInstrument` (broker layer); `to_instrument_key()` bridges
them. FX keys carry true currency legs; TradFi maps to CATI `FUTURES` (generic factor set). Asset-class
specific logic is configuration (factor sets, sessions), never a second engine.

## 8. FX reference dataset architecture

* Provider: **Dukascopy** public datafeed (`app/market_data/fx_reference.py`), no broker account; OANDA is
  not required anywhere. Provider-neutral protocol `FXReferenceProvider` (CSV provider also exists).
* `scripts/acquire_fx_reference_dataset.py`:
  * `probe` — one monthly file per candidate pair (all G10 pairs in market convention + USD/EUR crosses to
    liquid non-G10 currencies); availability + reason persisted in `fx_reference_availability`;
  * `broad` — hourly BID+ASK files per month for every available pair;
  * `deep` — minute BID+ASK per UTC day for pairs a venue lists as an FX execution instrument (discovered at
    run time) + USD majors; 15m bid/ask **derived** (`resample_quotes`, incomplete windows dropped);
  * `validate` — coverage, ingest-log gap markers, one-side-missing counts, negative spreads, triangular
    consistency (price-scale check).
* Stored in `fx_reference_quotes` (bid/ask OHLC, mid only when both sides exist, spread only when both
  exist — never 0, session label, `price_kind=REFERENCE_MARKET_PRICE`, `source_version`) and
  `fx_reference_ingest_log` (`FETCHED` / `NO_FILE` / `EMPTY` / `FAILED` per pair/period/side — the explicit
  gap marker; Saturdays logged `EMPTY: MARKET_CLOSED_SATURDAY` without a request).
* Timestamps: Dukascopy files are UTC-based (seconds from UTC day/month start); no zone conversion needed.
  Flat zero-volume padding bars (closed market) are dropped so a closed market is a gap.
* Currencies with an unvalidated price scale (HUF, CZK, RUB, THB, INR, KRW) are excluded with
  `UNVALIDATED_PRICE_SCALE` instead of being guessed.
* Location of the acquired data: `data/research/fx_reference_dukascopy.db` in the operator checkout
  (research data, not committed).
* **Acquired (2026-09-26):** probe -> **50 pairs available** (28 G10 + 22 USD/EUR crosses to SEK, NOK, DKK,
  PLN, SGD, HKD, CNH, ZAR, MXN, TRY, ILS); 12 excluded `UNVALIDATED_PRICE_SCALE`. Broad hourly tier
  **complete: all 50 pairs, 25 months** (12,939–12,956 bars for most pairs; shorter provider history for
  EURILS 8,100, USDILS 8,628, EURTRY 10,376, USDTRY 12,254; EURILS has 2 month files the provider does not
  serve, logged `NO_FILE`). Deep minute tier: EURUSD, GBPUSD, USDJPY — the pairs Bybit lists — for the
  60 days to 2026-09-25 (~61,600 1m bars and ~4,000 derived 15m bars each). Validation: 0 one-sided rows,
  0 negative spreads, triangular consistency on 31 crosses with max |rel diff| 6.0e-4.

## 9. Research vs certification vs execution universes

`app/market_data/universe.py`: roles `RESEARCH_UNIVERSE`, `TRAINING_UNIVERSE`, `CERTIFICATION_UNIVERSE`,
`EXECUTION_UNIVERSE`. A **frozen** universe (`build_frozen_universe_manifest`) is content-hashed over its
identity (window, criteria, rule version, members, metadata hash) — `generated_at` is not identity.
`load_frozen_universe` refuses an edited file. Every manifest says `execution_authorized: false`:
membership never implies execution. The EXECUTION universe of an account is derived per account
(section 14) from discovery + capability + certification.

  731 days, 70,176 bars per symbol at 15m;

  base, listed on/before the window start, **median daily quote volume ≥ $2M over the 30 closed days
  ending at the window end**, rank by that liquidity, target 150, minimum 100;
* result: **136 members** (the five original symbols included); 907 instruments considered, rejections
  recorded (306 too recent, 204 non-crypto, 130 not trading, 82 low liquidity, 44 quote asset,
  4 product type, 1 stablecoin base);

## 13. User broker API connection model

One connected account (encrypted credential version, permission evidence per version) exposes every
product the venue lists **and** the key may trade. There is no separate "forex bot key". Credentials are
never returned after creation, never logged (redaction), never in evidence or in any status response
(tested by key-name scan).

## 16. Internal capital routing

Existing, reused: `app/transfers/*` + `capital/planner.py`.

* flow: opportunity -> portfolio selection -> required capital -> planner outcome
  (`NO_ACTION_SHARED_COLLATERAL`, `LOGICAL_REALLOCATION`, `PHYSICAL_INTERNAL_TRANSFER_REQUIRED`,
  `INSUFFICIENT_SAFE_CAPITAL`, `TRANSFER_UNSUPPORTED`, `ACCOUNT_RECONCILIATION_REQUIRED`);
* transfer intent persisted before submission with an idempotency key (deterministic from the plan);
  statuses `REQUESTED, VALIDATING, BLOCKED, SUBMITTING, SUBMITTED, CONFIRMATION_PENDING, COMPLETED, FAILED,
  UNKNOWN, RECONCILIATION_REQUIRED` (the spec's PLANNED/RESERVED ≈ REQUESTED/VALIDATING, PENDING ≈
  CONFIRMATION_PENDING, CONFIRMED ≈ COMPLETED, RESOLUTION_PENDING ≈ UNKNOWN);
* a dispatched request without an answer -> `UNKNOWN`, never re-submitted; reconciliation by venue
  transfer history; no second transfer while one is unresolved; capital counts only after `COMPLETED`;
* full validation chain (ownership, asset/wallet allow-lists, amount/daily limits, source balance,
  reserves, pending risk reservations) — see `app/transfers/models.py::BlockReason`;
* same-account wallets only; **no withdrawal method or route exists**; withdraw-capable keys are refused.

In the CATI cycle the planner runs as evidence (`cati_capital_plan_evidence`, simulated outcome); nothing
is submitted by CATI (submission would require CATI execution authority, which is BLOCKED — section 23).

## 17. Unified-account logical allocation

Unified accounts return `NO_ACTION_SHARED_COLLATERAL` (the spec's TRANSFER_NOT_REQUIRED_UNIFIED_ACCOUNT).
Logical asset-class allocations are **risk budgets**: `PortfolioPolicy.asset_class_max_positions`
(e.g. `(("FX", 3),)`) is a hard feasibility constraint in the selector (`ASSET_CLASS_ALLOCATION_CAP`).
Default: empty (the account's slots are the limit). They never create capacity: hard account risk stays
superior.

## 18. Cross-asset portfolio / risk model

* Selection optimises the whole account book (existing + reserved + candidates, across bots sharing the
  broker account) with correlation, factor (incl. FX currency legs), sector and liquidity penalties.
* **Hard** currency-factor cap `PortfolioPolicy.max_net_currency_units = 2.0`: FX legs in pre-size units
  (LONG EURUSD = +EUR −USD; stablecoin quotes -> USD); a subset may not push |net| of any currency above the
  cap unless it does not worsen it. EURUSD+EURGBP+EURJPY long -> the third is refused
  (`CURRENCY_FACTOR_CAP:EUR`). A USDT-quoted crypto perpetual is not an FX USD leg.
* The notional-weighted exposure graph (`portfolio/currency_exposure.py`) remains available for hard-risk
  sizing checks; wiring it into the orchestrator sizing is a remaining item (section 32).
* Hard risk unchanged: 2.5% daily loss limit, capital ledger, slots, margin, leverage, broker constraints,
  emergency shutdown, reservations, reconciliation.

## 19. Security / API permissions

Required: read account/positions/orders, trade. Optional: internal transfer (positive evidence required to
move money). Never required: withdrawal — a key WITH withdrawal permission is refused for trading and
transfers (`API_KEY_WITHDRAW_PERMISSION_PRESENT`). Status APIs expose no credential material.

## 20. Multi-user isolation

Market intelligence (MarketState, GlobalMarketState, instrument catalog) is global and tenant-neutral.
Balances, positions, permissions, transfers, reservations and capital plans are keyed by
user + broker account; the status API resolves the account through the canonical resolver (404 for
another user's account). Two bots on one broker account aggregate at the account (selector input is the
account snapshot). No per-user state is placed in a shared cache.

## 21. Section 22 certification lifecycle

Policy (frozen, unchanged): P(expectancy>0) ≥ 0.95, 2× cost-stress floor −0.10 R, max holdout DD 10 R,
max single-segment positive share 0.50, min accepted evidence 100, max PBO 0.25, min positive
parameter-neighbour share 0.75, forward demo ≥ 30 executions AND ≥ 30 calendar days.

Lifecycle implemented here: broad dataset -> validate -> frozen certification-universe manifest (hash) ->
`certification plan/run --universe-manifest` (the universe hash enters the dataset identity; an incomplete
frozen universe is refused `FROZEN_UNIVERSE_INCOMPLETE_n_OF_m`) -> pre-holdout stages -> **holdout stays
closed** (`--open-holdout` is an explicit, separate operator decision).

  walk-forward folds, purge 12 h (48-bar label horizon), holdout region 2026-07-10 → 2026-09-23 (72.8 days),
  policy hash `55631f31…` (unchanged);

## 22. Section 24 GlobalMarketState

`contracts/global_market_state.py` + `market_state/global_state.py` + `market_state/global_state_store.py`:
deterministic (order-independent hash), causal (inputs after the decision boundary excluded), broker-neutral
(one input per canonical instrument), tenant-neutral (no account fields), versioned, hashed, lineage
(`input_market_state_ids`, `input_hash`). Components: risk_regime, crypto_context, usd_factor,
currency_factors, volatility, liquidity, breadth, correlation (`NOT_COMPUTED_IN_CYCLE`), funding_basis,
cross_asset_stress, event_risk, data_quality — each AVAILABLE with a value or UNAVAILABLE with a reason.
Built each decision epoch from the MarketStates the cycle already has (`SymbolEvaluation.market_state`),
persisted append-only in `cati_global_market_states`. It is **context/evidence only**: it does not admit,
veto, rank or size (that would be a governed policy change). Destination map: `contracts.global_market_state`
and `global_context` now **PRESENT**; Section 24 compliance = **PASS** (repository responsibilities). The
economic-calendar DATA is operationally stale (canonical DB feed ends 2026-05-29) and is surfaced as
STALE/UNAVAILABLE — an operational item, not a code gap.

## 23. Auto-activation model

`app/activation/model.py`: a capability's state is **computed** from prerequisites — all satisfied ->
ACTIVE; an unmet/unknown one -> BLOCKED (first reason); a structural impossibility -> UNSUPPORTED. Legacy
flags are operator overrides that can only switch **off** (`0/false/off` -> `OPERATOR_DISABLED`); unset or
truthy = AUTO. State changes are logged `[ACTIVATION] capability=… A -> B reason=…` and counted
(`activation_state_change_total`).

| Capability | Prerequisites | State now |
|---|---|---|
| CATI_CYCLE_SHADOW (evidence) | implementation | **ACTIVE** (forecasting reported AVAILABLE/UNAVAILABLE separately) |
| CATI_CAPITAL_ROUTING_SHADOW (evidence) | cycle shadow | **ACTIVE** |
| CATI_GLOBAL_MARKET_STATE (evidence) | cycle shadow | **ACTIVE** |
| CATI_ACTIVE_EXECUTION demo | phase ≥ M6, kill switch off, validated economic adapter, runtime authority switch | **BLOCKED** `GOVERNANCE_PHASE_M0_NO_CATI_AUTHORITY` (+ `RUNTIME_AUTHORITY_SWITCH_NOT_IMPLEMENTED`) |
| CATI_ACTIVE_EXECUTION live | + M7 scope granted / M8 | **BLOCKED** |
| CATI_EXIT_INTENT_ROUTING | active execution | **BLOCKED** |
| CATI_ML_AUTHORITY:<role> | PROMOTED model + phase ≥ ML minimum | **BLOCKED** `NO_PROMOTED_MODEL` (deterministic CATI estimator, never V2) |
| Broker CRYPTO/FX/TRADFI execution | declared + key + discovery + tradable + health | per account (matrix) |

Behaviour change to note: `CATI_CYCLE_SHADOW_ENABLED` and `CATI_CAPITAL_ROUTING_SHADOW_ENABLED` unset now
mean ACTIVE (evidence only). `CATI_ACTIVE_EXECUTION_ENABLED` unset now defers to governance (the boundary
refuses at M0 with `GOVERNANCE_NOT_AUTHORIZED`). The deprecated per-symbol diagnostic hooks
(`CATI_SHADOW_ENABLED`, `CATI_FULL_PIPELINE_SHADOW_ENABLED`) remain explicit opt-in diagnostics.

### 33.1 Section 7.11 refresh triggers (follow-up)

* `app/exchange/catalog_refresh.py`: one coalesced refresh request per venue/environment, raised by
  (a) an instrument-related venue API error on an order (`executor` order-rejection path; Binance codes
  -1121/-4140/-1111/-4014/-4023/-4003/-4005/-4164, Bybit/BingX unknown-symbol / not-trading / tick / step /
  minimum-notional messages; transport, auth, balance and rate-limit errors are not instrument errors; the
  environment comes from the client's registered host, never guessed) and (b) a CHANGE of the broker-reported
  account mode (`BybitTransferAdapter.account_mode`; first observations and unreadable modes are not changes).
  Only a bounded reason class is kept — never error text.
* Requests are consumed by the existing throttled `refresh_if_stale` (one venue call per venue/environment per
  5 min) on market-status reads and by the startup worker `discovery_refresh_loop` (every 5 min; refreshes
  only catalogs of venues with a connected account that are missing, older than 6 h or event-requested; a
  current catalog costs no venue call and no credential resolution; off switch
  `VENUE_DISCOVERY_REFRESH_ENABLED=0`). A successful sync clears the request; a failed one keeps it.
* A request changes no capability decision (Section 8/9 behaviour unchanged); an age-stale catalog stays
  fail-closed (`DISCOVERY_STALE`) until a refresh succeeds.
* `instruments.collect_cursor_pages`: the one cursor-pagination guard (repeated cursor / non-terminating chain
  -> error, never a truncated universe), used by `BybitClient.discover_instruments` and by
  `scripts/generate_capability_matrix.py` (which also refuses a non-zero `retCode`).
* Request state is in-process (single catalog writer); after a restart the age rule still applies.
