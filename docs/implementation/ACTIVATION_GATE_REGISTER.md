# Activation-gate register (master prompt section 29)

31 October 2026, baseline `d9010c2`. This is the machine-readable twin of
[activation_gates.json](activation_gates.json). Each lists the same 68 gates; if they ever differ, the JSON
is authoritative.

This register grants no authority. It lists every disabled trading function and every restriction that stops trading,
or a capability next to trading, from activating. For each one it records:
- what satisfies it and who owns it;
- how it is activated and revoked;
- which test proves the refusal.

Line numbers are for `HEAD d9010c2`, remapped for the three files this change edits (`production.py`, `gate.py`,
`market_entry_policy.py`). Other contributors are editing `certification.py`, `bingx.py`, `pipeline/execution.py`,
`readiness_gate.py`, `readiness_admin.py`, `main.py` and `protection.py` at the same time, so their working-tree lines
may have moved a few lines. "(HEAD)" marks a reference that is known to have moved.

## 2. Type A analysis: nothing converted

Every gate was tested against a strict rule. A gate is Type A only if both of these hold:
- the software it waits for is complete;
- the lock does not stand in for a certification, a risk limit, infrastructure or an owner decision.

**No gate meets that rule, so no lock was replaced with a configuration gate.** The closest cases:

- **`AUTH_BEARER_COMPAT` (E).**
  - The cookie-only clients are finished, and both backends are tested with the flag on and off.
  - What remains is the operator's observation window for clients outside this repository (EXT-F8-01). That is an
    operator decision, not missing software.
  - It is already a setting.
- **`BROKER_CYCLE_ASSIGNMENT_MODE` (D).**
  - `assigned` mode is built and tested.
  - The worker-kill drill on a staging host (EXT-WRK-01) has not run.
  - It is already a setting, with `owner` as the default.
- **`BUILD_PERMITS_LIVE` (E).**
  - The go-live software is complete: gate, ledger, consent and beta.
  - The constant is the owner's live release decision. It cannot become a setting: a setting would let a deploy
    make a build live-capable.
  - Section 30 replaced the single constant with a two-key, evidence-driven release (section 4). That makes the
    lock stronger; it is not a Type A conversion. Every development, CI and staging build stays incapable.
- **`LIVE_CERTIFICATION_NOT_PERMITTED_IN_THIS_BUILD`, `TRADFI_LIVE_NOT_PERMITTED_IN_THIS_BUILD`, `MAX_OPERABLE_STAGE = "M6"` (E).**
  - Each is a hard-coded release lock.
  - Live venue certification needs a live-money authorization (EXT-GL-01, EXT-DRILL-01).
  - Tradfi has no execution adapter.
  - M7 promotion has no route by design.
  - None is waiting only on software.
  - A live release must lift these together with the build keys. They are not tied to `live_build_status`:
    `certification.py` and `pipeline/family_governance.py` are outside this change's scope.

## 3. Findings (not changed here)

1. **`APPROVAL_MAX_VALIDITY_DAYS` was accepted as a policy key but read by nothing** — FIXED in the same pass
   (`app/golive/gate.py` `_operator_approval_audited`): an approval is in force at most that many days after its
   grant, whatever expiry its request stated; unset, condition 11 is `BLOCKED_PENDING_POLICY`
   (`APPROVAL_MAX_VALIDITY_DAYS_NOT_SET`). The value is the owner's. Test: `test_an_approval_is_never_open_ended`.
2. **Switching `LIVE_ORDER_SUBMISSION_ENABLED` off also stops protective orders.** In production,
   `require_broker_mutation_permission` refuses every mutation to a LIVE account while the flag is off: it raises
   `LiveOrderSubmissionDisabled` before the reduce-only branch, so stop replacement and flatten are refused too.
   - Revoking the go-live operator switch or a certification refuses new entries only. Protection and reduction go on
     (`test_revocation_refuses_new_entries_immediately_while_reducing_recovery_stays_allowed`).
   - Operators should use the switch or the kill switches to stop entries. The flag means "all real-money mutation off".
3. **`deploy/env.production.example` sets neither `GOLIVE_REVOCATION_ANCHOR` nor `PLATFORM_DATABASE_URL`.**
   - Without the anchor, every live entry fails `AUTHORIZATION_LEDGER_INTACT`.
   - Without the platform database, every production entry is refused, demo included.
   - The new profiles (`deploy/profiles/`) carry both.
4. **Some flags look like locks but enforce nothing.**
   - `REAL_TIME_NEWS_SHADOW_MODE` ("hard-locked") is read by nothing.
   - `TRADING_ENABLED` is only required to be true at startup, so it is not an off switch.
   - `LEGACY_V2_ENABLED` and `FALLBACK_ENGINE_ENABLED` are read only by the production profile.
   - The NEWS_*, TV_* and `ML_ENABLED` flags affect only the legacy runner, which never runs in production.
5. **In production, DEMO entries skip the global M0–M9 phase** (`governance/account_authority.py:46-50`). Demo is held
   back by the family gate: certification plus family stage M6. The global phase governs LIVE only, and no route moves it.
6. **The tradfi calendar guard is display-only.** The UNVERIFIED guard (`markets/guard.py`) runs only in the
   availability view. Tradfi stays blocked because no family declares a tradfi market and no tradfi adapter exists.
7. **Counsel review and country eligibility are not enforced in code.** A `DRAFT_PENDING_COUNSEL` document can be
   accepted, and the acceptance counts as current. No trading gate checks `UNDETERMINED` country eligibility.
8. **Revocation speed differs by kind.**
   - Takes a restart: most environment switches, which are read at process start.
   - Takes effect on the next entry, with no restart: kill switches, the operator live switch, consent, approvals,
     L-08 policy revocation and the family controls, which are database records read on every entry.
9. **No test proves these refusals directly:** `TRADING_ENABLED=false` in production; the ML promotion reason
   `GOVERNANCE_PHASE_BELOW_M6`; counsel status as a trading refusal.

## 4. The live-capable build (section 30)

`backends/shared/shared_lib/core/live_build.py`, `live_build_status()`. It is read-only and never raises. It reports
the first failing key as its reason.

**Key A: reviewed source.** Both parts are reviewed code:
- `BUILD_PERMITS_LIVE = True` at the reviewed code commit C0;
- a separate reviewed commit C1 that changes only `live_release_allowlist.py`, adding the manifest's SHA-256 to
  `APPROVED_LIVE_RELEASES`.

**Key B: the artifact.** A manifest at `/etc/cosmicforge/live-release/manifest.json`. It is baked only by
`deploy/containers/live-release.Dockerfile`, which CI, compose and the deploy scripts never use. It must:
- hash to a pinned entry;
- carry exactly the fields `schema`, `release_id`, `git_commit`, `source_tree_sha256`, `reviewers` (at least 2
  distinct), `approval_refs` and `created_at`;
- name a commit equal to the running build's `BUILD_VERSION`;
- name a source identity equal to the code this process actually runs.

The source identity excludes the allowlist module. That is how C1 can pin a manifest that names C0 without the hash
having to contain itself.

**Reason codes:** `LIVE_NOT_PERMITTED_IN_THIS_BUILD`, `LIVE_RELEASE_ALLOWLIST_INVALID`,
`LIVE_RELEASE_NOT_APPROVED_IN_SOURCE`, `LIVE_RELEASE_MANIFEST_ABSENT`, `LIVE_RELEASE_MANIFEST_UNREADABLE`,
`LIVE_RELEASE_MANIFEST_MALFORMED`, `LIVE_RELEASE_REVIEWERS_INSUFFICIENT`, `LIVE_RELEASE_APPROVAL_REFS_MISSING`,
`LIVE_RELEASE_MANIFEST_NOT_APPROVED`, `LIVE_RELEASE_BUILD_COMMIT_UNKNOWN`, `LIVE_RELEASE_COMMIT_MISMATCH`,
`LIVE_RELEASE_SOURCE_UNREADABLE`, `LIVE_RELEASE_SOURCE_MISMATCH`, `LIVE_BUILD_CAPABLE`.

**Who reads it:**
- go-live condition 15;
- the K4 startup refusal of `LIVE_ORDER_SUBMISSION_ENABLED=true`;
- the L-08 LIVE policy;
- the configuration-profile validator;
- the status surfaces: `GET /api/v1/admin/golive/build`, and `configuration_matrix()["LIVE BUILD"]` on the runtime
  status and `/health` production configuration.

**A capable build authorizes nothing.** Every other go-live condition, the operator's flag and every transport gate
stay in force. `scripts/release/live_release_manifest.py` validates a manifest and prints its hash for review. It
refuses to run in CI and writes nothing.

## 7. Maintenance

- Add a gate to both files in the same commit. The JSON's `counts` must match its `gates`.
- Moving a gate between types needs the reason in `type_justification`.
- A move to Type A also needs the file that proves the supporting software is complete.
- Converting a Type A lock needs a refusal test both ways: off refuses, on admits only with the evidence present.
