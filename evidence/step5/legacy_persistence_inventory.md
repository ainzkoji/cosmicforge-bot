## Findings

- **NUMERIC(38,18) cannot hold every legacy float.** Money is computed in binary floats, and a float result carries up to 17 significant digits at any magnitude: a fee `notional * 0.0004` such as `0.0062978382397085135` has 19 fractional digits (about 1.5 % of such fees). NUMERIC(38,18) would round them at the 18th place. Decision (coordinator): legacy monetary columns use unconstrained `NUMERIC`, which holds the shortest decimal (`repr`) of every finite binary64 exactly, subnormals included (`test_legacy_money_postgres.py`); the platform layer keeps NUMERIC(38,18) for exact decimal input. The migration drill still reports, never rounds, any value a target column with a declared scale cannot hold.
- PostgreSQL's own `float8 -> numeric` cast rounds to 15 significant digits (`0.30000000000000004` -> `0.3`): values must be bound as `Decimal(repr(x))`, never cast on the server.
- `trades` has two divergent `CREATE TABLE IF NOT EXISTS` definitions (trade_tracker.py vs analytics_service.py); the first to run decides NOT NULL constraints.
- The legacy schema has no version table: PostgreSQL needs its own versioned baseline for it.
- Time is stored three ways (ISO text from `isoformat()`, SQLite `CURRENT_TIMESTAMP` text without `T`/zone, epoch integers); a port must keep each column's representation, not normalise it silently.
